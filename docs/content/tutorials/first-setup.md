You'll write the config that tells stomp which of your directories belong to
which grant, check it with `stomp doctor` (including a mistake made on
purpose), and read your first per-grant usage report. At the end you'll have
the config every other tutorial builds on. If stomp isn't on the cluster yet,
start with [Install stomp](@/getting-started/install.md).

## Create a starter config

Run `stomp init` on a login node:

```sh
stomp init
```

```text
Wrote ~/.config/stomp/config.toml with 8 grant stubs, one per top-level directory.
Next: edit it to define your grants, check it with `stomp doctor`, then run `stomp usage`.
```

stomp looked at the top-level directories of your home and wrote a
commented-out `[[grant]]` stub for each one. The file starts like this:

```toml
# stomp configuration, generated by `stomp init` on 2026-11-18.
#
# Each [[grant]] block claims one or more directories, and every file under
# them counts toward that grant. A directory can belong to only one grant.
# Optional grant fields: title, pi, start and end (dates such as 2027-06-30).
#
# Check this file with `stomp doctor`, then run `stomp usage`.

[general]
roots = ["~"]

# Settings for the Slurm tasks stomp will submit for scans and archiving.
# [slurm]
# account   = "myaccount"
# partition = "standard"
# time      = "12:00:00"
# cpus      = 8
# mem       = "16G"

# --------------------------------------------------------------------------
# Directories in ~ (POSIX).
# Uncomment and edit a block for each grant. A grant with several
# directories lists them all in `dirs`.
# --------------------------------------------------------------------------

# ~/containers: size not measured (not on CephFS)
# [[grant]]
# id    = "CONTAINERS"
# title = "containers"
# dirs  = ["~/containers"]

# ~/forest_plots: size not measured (not on CephFS)
# [[grant]]
# id    = "FOREST_PLOTS"
# title = "forest_plots"
# dirs  = ["~/forest_plots"]
…
# Hidden directories in ~. These usually hold settings, caches and
# software environments, and count as unassigned unless a grant claims them:
#   ~/.cache: size not measured (not on CephFS)

# Files directly in ~: 28 B in 1 file (unassigned).
```

A few things to notice:

- **`roots`** lists the top-level directories stomp manages. `~` (your home)
  is the default. Every grant directory must be inside one of the roots.
- **Each stub** has an ID made from the directory's name, and the directory
  in `dirs`. You'll replace these with your real grants.
- **The size line above each stub** depends on the filesystem. These examples
  come from a test machine without CephFS, so it says "size not measured". On
  the cluster's CephFS home, it shows each directory's size, file count and
  when it last changed, and lists the largest directories first.

`stomp init` never overwrites a config. Run it again and it stops with an
error that points to `stomp init --print`, which prints a fresh template
instead of writing one. To manage more than your home, give `--root` once for
each directory, such as a project space.

## Decide which directories belong to which grant

A grant directory counts its whole subtree: every file under it, however deep,
counts toward that grant. So the question for each directory is "did one grant
pay for everything in here?"

Alex's home holds these top-level directories:

| Directory | What's in it | Grant |
|-----------|--------------|-------|
| `~/soil_carbon` | Sentinel-2 imagery, field data, analysis code | `NSF-2231` |
| `~/soil_carbon_runs` | Model runs for the same project | `NSF-2231` |
| `~/marsh_mapping` | Orthomosaics, classified tiles, field photos | `USDA-1180` |
| `~/forest_plots` | Lidar and plot inventories | `EPSCOR-T2` |
| `~/scratch` | Temporary files from several projects | none |
| `~/papers` | Manuscripts | none |
| `~/miniconda3`, `~/containers` | Software every project uses | none |
| `~/.cache` and other hidden directories | Settings and caches | none |

Some guidelines:

- **Not everything needs a grant.** Directories no grant claims are reported
  together as unassigned, so you can see how much of your space isn't
  attributed to anything.
- **One grant can have several directories**, as `NSF-2231` does here.
- **A grant directory doesn't have to be top-level.** If one manuscript
  belonged to a single grant, Alex could add `~/papers/soil_carbon_2026` to
  that grant's `dirs` and leave the rest of `~/papers` unassigned.
- **One directory can't be split between grants.** If a directory mixes two
  grants' data, list its subdirectories separately, or move the data so each
  grant's lives in its own directory.

## Write the grant blocks

Open `~/.config/stomp/config.toml` in an editor. Delete the stubs (or leave
them; comments are ignored) and add one `[[grant]]` block per grant:

```toml
[[grant]]
id    = "NSF-2231"
title = "Soil carbon dynamics under forest management"
pi    = "J. Rivera"
start = 2024-09-01
end   = 2027-08-31
dirs  = ["~/soil_carbon", "~/soil_carbon_runs"]

[[grant]]
id    = "USDA-1180"
title = "Coastal marsh mapping"
pi    = "M. Chen"
start = 2022-07-01
end   = 2026-06-30
dirs  = ["~/marsh_mapping"]

[[grant]]
id    = "EPSCOR-T2"
title = "Forest plot remote sensing"
pi    = "J. Rivera"
start = 2025-06-01
end   = 2028-05-31
dirs  = ["~/forest_plots"]
```

What each key means:

- **`id`** is the name you'll type in commands and see in reports. It may use
  letters, digits, `-`, `_` and `.` (up to 64 characters, not starting with
  `-` or `.`), because it also appears in file names and archive IDs. `stomp`
  and `unassigned` are reserved.
- **`title`** and **`pi`** are for people: they head `stomp report grant`,
  and the browser shows the title.
- **`start`** and **`end`** are plain dates, written without quotes. With
  quotes, TOML reads them as text and stomp rejects the file. stomp uses `end`
  in `stomp report lifecycle`, which lists grants that have ended or are
  about to, and in policies that propose archiving a grant's data some time
  after it ends.
- **`dirs`** lists the grant's directories. A leading `~` and environment
  variables such as `$USER` are expanded.

Only `id` is required. A grant without `dirs` gets no storage, but can still
collect compute jobs.

## Check the config with stomp doctor

`stomp doctor` reads the config, checks it against the rules for grant
directories, and looks at the rest of your environment. To see how it reports
problems, make two mistakes on purpose first. Change `NSF-2231`'s second
directory to `~/soil_carbon_run` (a typo), and add the imagery directory to
`EPSCOR-T2`, as if the satellite imagery had been bought with EPSCOR money:

```toml
[[grant]]
id    = "NSF-2231"
…
dirs  = ["~/soil_carbon", "~/soil_carbon_run"]

…

[[grant]]
id    = "EPSCOR-T2"
…
dirs  = ["~/forest_plots", "~/soil_carbon/imagery"]
```

Now run doctor:

```sh
stomp doctor
```

```text
FAIL  config       ~/.config/stomp/config.toml: ~/soil_carbon/imagery (grant EPSCOR-T2) is inside ~/soil_carbon (grant NSF-2231); grant directories must not overlap
warn  config       grant NSF-2231: ~/soil_carbon_run does not exist
ok    data dir     ~/.local/share/stomp is writable
ok    catalog      88.0 KiB: 0 measurement(s), 0 scan(s), 0 job record(s)
info  accounting   not imported yet; `stomp jobs sync` does it
ok    slurm        sbatch, squeue and sacct found
ok    slurm        scrontab found; recurring work can use it if the site allows
info  threads      8 worker thread(s)

1 failure(s) and 1 warning(s).
```

Doctor found both mistakes, and they're of different kinds.

The `FAIL` is the overlap. Every file under `~/soil_carbon` already counts
toward `NSF-2231`, so `~/soil_carbon/imagery` can't also count toward
`EPSCOR-T2`. A config with a failure like this is unusable: every command that
needs it stops with the same message, lists the config's warnings under it,
and exits with status 2:

```sh
stomp usage
```

```text
stomp: error: ~/.config/stomp/config.toml: ~/soil_carbon/imagery (grant EPSCOR-T2) is inside ~/soil_carbon (grant NSF-2231); grant directories must not overlap
  warning: grant NSF-2231: ~/soil_carbon_run does not exist
```

The `warn` is the typo. A directory that doesn't exist is only a warning,
because it may have been archived or renamed on purpose. On its own it
wouldn't stop stomp, but most commands would print it each time until you
deal with it.

Fix both. The imagery is part of the soil carbon work, so take it out of
`EPSCOR-T2` (`dirs = ["~/forest_plots"]`), and correct the typo to
`~/soil_carbon_runs`. Then run doctor again:

```sh
stomp doctor
```

```text
ok    config       ~/.config/stomp/config.toml: 3 grant(s), 1 root(s), 0 destination(s)
ok    data dir     ~/.local/share/stomp is writable
ok    catalog      88.0 KiB: 0 measurement(s), 0 scan(s), 0 job record(s)
info  accounting   not imported yet; `stomp jobs sync` does it
info  filesystem   ~ is not CephFS, so measuring it means walking every file
ok    slurm        sbatch, squeue and sacct found
ok    slurm        scrontab found; recurring work can use it if the site allows
info  threads      8 worker thread(s)
info  schedule     daily runs are off; `stomp schedule enable` keeps usage, accounting, scans and proposals current

No problems found.
```

Each line starts with `ok`, `info`, `warn` or `FAIL`. Besides the config,
doctor checks that stomp's data directory (`~/.local/share/stomp`) is
writable, reports how much its catalog holds, finds the Slurm commands, and
says how many threads stomp will use. The `filesystem` line matters: on
CephFS it says usage is instant, and elsewhere, as here, that measuring means
walking every file. The `info` lines aren't problems: they describe your
setup and what isn't turned on yet. Doctor exits with status 1 if anything
failed, so you can use it in scripts.

### The rules for grant directories

stomp checks these every time it reads the config:

- **A directory belongs to one grant.** The same directory in two grants is a
  failure ("is claimed by both … a directory can belong to only one grant"),
  and so is one grant's directory inside another grant's, as above.
- **Inside one grant, overlaps are harmless.** Listing a directory twice, or
  listing a directory inside another of the same grant's directories, is a
  warning ("is listed nested inside another of its directories; it is
  counted once").
- **Every grant directory must be inside a root.** Otherwise doctor fails
  with "… is not inside any of general.roots". stomp resolves symlinks first,
  so a link in your home that points to project space counts as being in
  project space; the message then adds "(it resolves to …; is it a
  symlink?)". To include such a directory, add the directory it lives in to
  `roots`, for example `roots = ["~", "/project/rivera"]`. Roots can't be
  inside each other.
- **A missing directory is a warning**, as you saw. A path that exists but is
  a file, not a directory, is a failure.

## Read your first usage report

With a clean config, ask for storage per grant:

```sh
stomp usage
```

```text
stomp: ~ is not on CephFS, so measuring it means walking every file. This can take a while.
Measured 2026-11-18 18:03 EST

ROOT   FILESYSTEM      SIZE   FILES   QUOTA
~      POSIX        1.7 TiB   1,381   —

GRANT          DIRS        SIZE   FILES   LAST CHANGE
USDA-1180         1   913.9 GiB     457   just now
NSF-2231          2   592.5 GiB     166   just now
EPSCOR-T2         1   179.2 GiB      46   just now
(unassigned)      —    74.9 GiB     712   just now
-----------------------------------------------------
TOTAL                   1.7 TiB   1,381   just now
```

The first line appears only on filesystems that don't keep directory totals.
On the cluster's CephFS, stomp reads the totals CephFS keeps for every
directory, so `stomp usage` is instant even for millions of files, and the
line isn't printed. Later outputs on this page leave it out.

The first table describes each root:

- **FILESYSTEM**: `CephFS` or `POSIX` (anything else).
- **SIZE** and **FILES**: everything under the root.
- **QUOTA**: on CephFS, the quota that applies to the root (it may be set on
  a directory above it) and how much of it is used, or `none set`. Elsewhere
  stomp can't see quotas and shows `—`.

The second table has one row per grant, largest first:

- **DIRS**: how many of the grant's directories were measured. If one is
  missing, this reads `1 of 2` and only the others count; if none exist, the
  other columns show `—`.
- **SIZE**: the total size of the files, as `ls -l` reports them, in binary
  units (1 GiB is 1024³ bytes).
- **FILES**: how many files, counting anything that isn't a directory.
- **LAST CHANGE**: how long ago anything under the grant's directories last
  changed, from the newest change time (ctime) of anything in them.
- **(unassigned)**: everything under the root that no grant claims. For Alex
  that's `~/scratch`, `~/papers`, the software, the hidden directories
  (including stomp's own data in `~/.local/share/stomp`), and the file
  directly in `~`. With several roots, there's one such row per root.
- **TOTAL**: the sum, which matches the root's size.

Every `stomp usage` run is saved to the usage history, which `stomp changes`
and `stomp report history` use. Add `--no-record` when you just want a look.
Once you have archives at a remote destination, or archive proposals from
policies, `stomp usage` lists those below the table too.

## See which grant each directory belongs to

`stomp du` shows directory sizes, like `du`, with a GRANT column:

```sh
stomp du ~
```

```text
     SIZE   FILES   LAST CHANGE   GRANT                                     PATH
  1.7 TiB   1,381   just now      contains NSF-2231, USDA-1180, EPSCOR-T2   ~
913.9 GiB     457   just now      USDA-1180                                   marsh_mapping/
509.6 GiB      66   just now      NSF-2231                                    soil_carbon_runs/
179.2 GiB      46   just now      EPSCOR-T2                                   forest_plots/
 82.8 GiB     100   just now      NSF-2231                                    soil_carbon/
 59.0 GiB       2   just now      —                                           scratch/
  7.3 GiB     501   just now      —                                           miniconda3/
  5.0 GiB      82   just now      —                                           containers/
  3.5 GiB     120   just now      —                                           .cache/
117.2 KiB       3   just now      —                                           papers/
 88.0 KiB       2   just now      —                                           .local/
  1.2 KiB       1   just now      —                                           .config/
     28 B       1                 —                                           (files here)
```

The GRANT column shows the grant a directory counts toward, `—` if none, or
`contains …` for a directory that isn't a grant directory itself but holds
some. The `(files here)` line is the files directly in the directory, outside
any subdirectory. This is a quick way to check your mapping: every directory
you meant to assign should show its grant. `stomp du` works without a config
too, just without the GRANT column. The next tutorial uses it to dig deeper.

## Get the output in other formats

Commands that print tables accept `--format table|csv|json|md`. Markdown is
handy for pasting into a progress report or an issue:

```sh
stomp usage --format md --no-record
```

```text
Measured 2026-11-18 18:03 EST

| ROOT | FILESYSTEM | SIZE | FILES | QUOTA |
| --- | --- | ---: | ---: | --- |
| ~ | POSIX | 1.7 TiB | 1,381 | — |

| GRANT | DIRS | SIZE | FILES | LAST CHANGE |
| --- | ---: | ---: | ---: | --- |
| USDA-1180 | 1 | 913.9 GiB | 457 | just now |
| NSF-2231 | 2 | 592.5 GiB | 166 | just now |
| EPSCOR-T2 | 1 | 179.2 GiB | 46 | just now |
| (unassigned) | — | 74.9 GiB | 712 | just now |
| TOTAL |  | 1.7 TiB | 1,381 | just now |
```

CSV and JSON are for spreadsheets and scripts. They give raw byte counts, full
paths and RFC 3339 times instead of rounded sizes and "2h ago". In CSV the
unassigned row's grant is `unassigned`. stomp's notes and warnings go to
standard error, so redirecting saves only the data:

```sh
stomp usage --format csv --no-record > usage.csv
```

```text
stomp: ~ is not on CephFS, so measuring it means walking every file. This can take a while.
```

`--json` is a shorter way to write `--format json`. The
[output formats reference](@/reference/formats.md) lists every column.

## Tell stomp how to submit Slurm tasks

Heavy work, such as detailed scans and archiving, runs as Slurm jobs that
stomp submits for you, called tasks. They use the `[slurm]` settings in your
config. Uncomment the block `stomp init` wrote and fill it in:

```toml
# Settings for the Slurm tasks stomp will submit for scans and archiving.
[slurm]
account   = "lab-rivera"
partition = "standard"
time      = "08:00:00"
cpus      = 8
mem       = "16G"
```

- **`account`** is the Slurm account the tasks are charged to: use the one
  you put in your own job scripts' `#SBATCH --account` line. Without it,
  Slurm uses your default account, and some clusters reject jobs that don't
  name one.
- **`partition`**, **`time`** and **`mem`** are passed to Slurm as they are.
  Leave one out and the cluster's default applies. A task that reaches its
  time limit saves its progress and submits itself again to continue, so
  `time` doesn't need to cover the biggest job you can imagine.
- **`cpus`** defaults to 8. stomp uses at most `scan.max_threads` threads
  (8 by default) to spare the shared file servers, so more CPUs than that
  don't make a task faster.

Any task command also takes `--account`, `--partition`, `--time`, `--cpus`
and `--mem` to override these once.

To check that tasks submit, run doctor as a task. Its checks take seconds, so
it asks for a small job (1 CPU, 1 GB, 10 minutes) instead of your `[slurm]`
sizes, which lets it start sooner:

```sh
stomp doctor --submit
```

```text
Submitted the checks as Slurm job 4810233. When it finishes, `stomp tasks show doctor-20261118-180325-c4e5` points to the output.
```

When the job has run:

```sh
stomp tasks show doctor-20261118-180325-c4e5
```

```text
Task      doctor-20261118-180325-c4e5
Kind      doctor
Status    done
Created   2026-11-18 18:03
Updated   2026-11-18 18:03
Jobs      4810233
Message   all checks passed
Script    ~/.local/share/stomp/tasks/doctor-20261118-180325-c4e5/task.sh
Log       ~/.local/share/stomp/tasks/doctor-20261118-180325-c4e5/slurm-4810233.out
```

The log holds doctor's report as seen from a compute node. The script is the
batch script stomp generated, so you can see exactly what it asked Slurm for:

```sh
grep -E '^#SBATCH --(cpus|time|mem|partition|account)' ~/.local/share/stomp/tasks/doctor-20261118-180325-c4e5/task.sh
```

```text
#SBATCH --cpus-per-task=1
#SBATCH --time=00:10:00
#SBATCH --mem=1G
#SBATCH --partition=standard
#SBATCH --account=lab-rivera
```

The CPUs, time and memory are doctor's small defaults; the partition and
account came from `[slurm]`. If Slurm refuses a task, stomp stops with
`sbatch failed:` followed by Slurm's own message.
